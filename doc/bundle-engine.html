AI Telecom Bundles Engine / Single-Operator Design

Single-Operator Causal AI Specification for Bundle Incrementality, Cannibalization, and GA-Based Bundle Optimization

This document defines a single-operator-only solution for deciding whether a new telecom bundle, or an optimized version of an existing bundle, creates true incremental revenue or simply cannibalizes the operator's current portfolio. The design assumes the system works on one operator's weekly data only and uses internal variation across region, channel, segment, and time to estimate causal effects.

Scope: exactly one telecom operator Time grain: weekly / isoWeek Goal: maximize net incremental portfolio revenue Search engine: genetic algorithm seeded from this operator's portfolio

Scope and Non-Negotiable Assumptions

This system is single-operator only. It must use data from one operator and optimize decisions only for that operator's current and future portfolio.

1.1 Explicit Scope Rules

  • Do not compare multiple operators.
  • Do not pool different operators in the causal training data.
  • Do not estimate effects based on cross-operator differences.
  • Do not use other operators as controls for treatment unless the business later changes the system scope.

1.2 What the Dataset Represents

The dataset should represent one operator's product portfolio over time. If an operator_id column exists, it is only for lineage and metadata, not a modeling dimension. 

Modeling grain inside one operator:
region x channel x segment x product x iso_week

Optional simplified grain if some dimensions are unavailable:
region x product x iso_week
channel x product x iso_week
segment x product x iso_week
Critical implication: because there is only one operator, the causal variation must come from internal rollout differences: region-level timing, channel-level timing, segment eligibility, or phased launches over time.

Questions the System Must Answer

Bundle-Level Questions

  • Will this candidate bundle create new value for the operator?
  • Will this bundle improve the operator's total weekly portfolio revenue?
  • Is the bundle incremental or cannibalistic after considering product substitution?

Portfolio-Level Questions

  • Which existing bundles are likely to lose sales if this new bundle is launched?
  • How much weekly revenue is expected to be lost by each affected bundle?
  • What is the net portfolio gain after all positive and negative product interactions?
Required output for each candidate:
  • Predicted gross adoption
  • Predicted new-bundle revenue
  • Predicted revenue stolen from existing bundles
  • Predicted net incremental revenue for the operator portfolio
  • Ranked list of the most affected current products
  • Confidence-aware accept or reject signal
4

What Changes in a Single-Operator Setup

In a multi-operator design, one could exploit variation across operators. In this design, that is not allowed. All estimation must come from changes inside the same operator over time.

4.1 Units of Analysis

Let u denote an internal unit of the operator. Depending on data availability, u can be:

region channel segment region x channel region x segment channel x segment region x channel x segment

4.2 Source of Causal Variation

  • Bundle launched in some regions before others
  • Bundle launched on digital channel before retail
  • Offer opened to prepaid before postpaid
  • Pilot rollout in selected internal markets before wider release
  • Feature or price change applied first to only part of the operator base
If the operator always launches every bundle everywhere at the same moment, the causal confidence will be weak. In that case the business should create internal variation through phased rollout, holdout regions, holdout channels, or segment-based eligibility rules.
5

Formal Problem Definition

Let k denote a candidate bundle, j an existing bundle in the operator portfolio, u an internal operator unit, and t a week.

5.1 Treatment Definition

T_k(u, t) = 1 if candidate bundle k is available in unit u at week t
T_k(u, t) = 0 otherwise

5.2 Outcomes

Y_portfolio(u, t) = total portfolio revenue of the operator in unit u at week t
Y_j(u, t)         = revenue of existing product j in unit u at week t
Y_k(u, t)         = revenue of candidate/new product k in unit u at week t

5.3 Causal Quantities

Portfolio Lift of candidate k:
Delta_portfolio(k) =
  E[Y_portfolio | do(T_k=1)] - E[Y_portfolio | do(T_k=0)]

Effect of candidate k on existing product j:
Delta_j<-k =
  E[Y_j | do(T_k=1)] - E[Y_j | do(T_k=0)]

Total Cannibalized Revenue:
CannibalizedRev(k) =
  sum over j of max(0, -Delta_j<-k)

Positive Spillover Revenue:
PositiveSpilloverRev(k) =
  sum over j of max(0, Delta_j<-k)

Net Incremental Revenue:
NetIncrementalRev(k) =
  Delta_portfolio(k)

5.4 Business Interpretation

  • If NetIncrementalRev(k) > 0, the bundle is incremental at the operator-portfolio level.
  • If the new bundle sells well but NetIncrementalRev(k) <= 0, it is cannibalistic.
  • Products with the most negative Delta_j<-k are the bundles most harmed by the new product.

Causal Identification Strategy

The system must estimate causal effects from internal differences inside the operator, not from simple before/after trends.

7.1 Preferred Historical Method

Use a within-operator panel causal estimator centered on staggered launch timing across internal units. In practical terms, this is a difference-in-differences or event-study design using region, channel, segment, and week variation inside the operator.

7.2 Treatment Units

  • u = region when rollout differs by geography
  • u = channel when rollout differs by sales channel
  • u = segment when rollout differs by customer segment
  • u = region x channel or region x segment when more granularity is available

7.3 Core Assumptions

  • Treated and untreated internal units would have followed similar trends absent the launch.
  • Marketing and promo differences are controlled as explicit covariates.
  • The launch flag correctly represents real product availability.
  • No major internal operational shock is wrongly attributed to the launch.

7.4 Required Controls

  • Week-of-year and seasonal calendar controls
  • Holiday and payday effects
  • Marketing spend and campaign intensity
  • Region fixed effects
  • Channel fixed effects
  • Segment fixed effects
  • Competitor pressure index where available
  • Portfolio age and maturity signals
If historical launches have no internal staggered rollout at all, then future production deployment should deliberately introduce pilot launches, holdout units, or controlled phased rollout. Otherwise the model can still rank likely candidates, but the confidence in incrementality estimates will be materially weaker.
8

Modeling Stack

The solution should be implemented as several coordinated models. One single model is not enough.

Model A: Popularity / Adoption Model

Purpose: estimate gross uptake of a candidate bundle inside the operator.

  • Target: gross_adds, active_subscribers, or first-N-week uptake
  • Uses only this operator's historical bundles
  • Output is a demand prior, not the final business answer

Model B: Within-Operator Launch Effect Model

Purpose: estimate causal effect of a launch on total portfolio revenue within internal units.

  • Outcome: Y_portfolio(u,t)
  • Uses internal variation by unit and week
  • Returns portfolio lift from historical launches

Model C: Pairwise Cannibalization Model

Purpose: estimate effect of candidate bundle k on each existing bundle j.

  • Outcome: Delta_j<-k
  • Training rows describe interactions between launched bundles and incumbents
  • Returns a ranked affected-product list

Model D: Candidate Effect Generalizer

Purpose: extrapolate from observed launches to unseen GA-generated bundles.

  • Learns how bundle attributes and context change causal impact
  • Used to score candidates that have never been launched before
  • Should produce mean effect and uncertainty estimate

8.1 Pairwise Interaction Features

  • Price gap between candidate and incumbent
  • Relative price per GB and price per minute
  • Benefit overlap score across data, voice, SMS, and validity
  • Target segment overlap
  • Channel overlap
  • Bundle family similarity
  • Margin attractiveness difference
  • Incumbent popularity / maturity / churn profile
C(k, j, context) =
predicted causal effect of launching candidate k
on the revenue of current product j
inside the same operator

If C(k, j, context) < 0, product j is cannibalized by k
Because the system is single-operator, data volume will usually be lower than a multi-operator setup. Use pooled models with shrinkage across products, regions, channels, and segments rather than many tiny isolated models.
9

Candidate Bundle Scoring

The scenario scorer is the core decision layer used by the GA. It converts a candidate bundle plus a current portfolio snapshot into a causal business recommendation.

9.1 Scoring Sequence

  1. Estimate candidate gross adoption using the popularity model.
  2. Estimate revenue generated directly by the new bundle.
  3. Estimate impact on every existing product in the current operator portfolio.
  4. Aggregate revenue losses from harmed incumbents.
  5. Aggregate positive spillovers if any exist.
  6. Compute net incremental portfolio revenue.
  7. Apply confidence-aware decision logic.

9.2 Core Equations

PredictedNewBundleRevenue(k) =
  predicted_gross_adds(k) * expected_revenue_per_add(k)

CannibalizedRev(k) =
  sum over existing products j of max(0, -C(k, j, context))

PositiveSpilloverRev(k) =
  sum over existing products j of max(0, C(k, j, context))

NetIncrementalRev(k) =
  PredictedNewBundleRevenue(k)
  + PositiveSpilloverRev(k)
  - CannibalizedRev(k)
  - LaunchCost(k)
  - PromoCost(k)

9.3 Cannibalization Ratio

CannibalizationRatio(k) =
  CannibalizedRev(k) / max(epsilon, PredictedNewBundleRevenue(k))

9.4 Confidence-Aware Score

RiskAdjustedLift(k) =
  LowerConfidenceBound(NetIncrementalRev(k))

Example:
LCB = mean_lift - z * standard_error
Production acceptance rule: accept a candidate only if:
  • RiskAdjustedLift(k) > 0
  • CannibalizationRatio(k) is below threshold
  • No protected current product exceeds maximum allowed loss
  • All pricing and margin constraints are valid
10

Genetic Algorithm Integration

The GA must start from the current portfolio of this operator only. It can mutate current bundles, generate adjacent variants, or synthesize new bundles within business-safe boundaries.

10.1 Initial Population

Initial population =
current operator portfolio
+ slight feature mutations
+ allowed new combinations within product design rules

10.2 Chromosome Structure

Chromosome = [
  price,
  data_gb,
  voice_min,
  sms_count,
  validity_days,
  segment_target,
  channel_scope,
  bundle_family,
  promo_depth,
  free_addons,
  fair_use_policy,
  optional_business_flags
]

10.3 Fitness Function

Fitness(k) =
    w1 * normalize(RiskAdjustedLift(k))
  + w2 * normalize(PopularityScore(k))
  - w3 * normalize(CannibalizationRatio(k))
  - w4 * normalize(OverlapPenalty(k))
  - w5 * normalize(ComplexityPenalty(k))

10.4 Constraint Set

  • Price must stay within approved commercial ranges.
  • Bundle contents must satisfy technical feasibility.
  • Margin must stay above minimum acceptable threshold.
  • Net incremental revenue lower bound must be positive for recommended candidates.
  • Protected flagship products cannot be excessively harmed.
The popularity score should not dominate the fitness function. A candidate may be highly popular and still be rejected if it mostly steals users from profitable current products.

End-to-End Pipeline

Step 1: Build Weekly Panel

  • Assemble one operator's weekly sales table
  • Create internal units by region, channel, segment
  • Join product catalog and event metadata
  • Create portfolio-level weekly aggregates

Step 2: Build Event Registry

  • Store launches, price changes, feature changes, retirements
  • Track exact unit-level availability by week
  • Track phased rollout scope

Step 3: Train Base Models

  • Train popularity model
  • Train portfolio lift estimator
  • Train pairwise cannibalization model
  • Train effect generalizer for unseen candidates

Step 4: Scenario Scoring Service

  • Input: candidate bundle + current portfolio snapshot + rollout context
  • Output: adoption, new revenue, cannibalization, affected products, net lift, confidence band

Step 5: GA Search Loop

  • Generate candidates
  • Score each candidate via scenario scorer
  • Select by causal fitness, not raw demand
  • Return top ranked bundles for recommendation or pilot launch

Validation and Monitoring

12.1 Offline Validation

  • Backtest on historical launches within the same operator.
  • Check pre-trends between treated and untreated internal units.
  • Run placebo launch dates to test false positive lift.
  • Compare predicted harmed products against realized post-launch declines.
  • Measure whether confidence bands are calibrated.

12.2 Online Validation

  • Use phased rollout when launching top candidates.
  • Track predicted versus realized portfolio lift week by week.
  • Track predicted versus realized incumbent bundle losses.
  • Retrain and recalibrate after each validated launch cycle.

Reference Pseudocode

14.1 Training Phase

# 1) Build weekly panel for one operator only
panel = build_weekly_panel(
    raw_sales,
    product_catalog,
    event_table,
    internal_controls
)

# panel grain:
# region x channel x segment x product x iso_week

# 2) Train popularity / adoption model
popularity_model.fit(
    X = panel[candidate_features + context_features],
    y = panel["gross_adds"]
)

# 3) Estimate historical launch effects within the operator
portfolio_lift_model.fit(
    data = panel,
    treatment = "availability_flag",
    outcome = "portfolio_revenue",
    unit_keys = ["region_id", "channel_id", "segment_id"],
    time_key = "iso_week",
    controls = confounder_features
)

# 4) Build pairwise rows:
# each row describes how a launched bundle k affected existing bundle j
pairwise_rows = build_pairwise_rows(
    panel=panel,
    event_table=event_table,
    current_products=current_portfolio_products
)

pairwise_cannibal_model.fit(
    X = pairwise_rows[pair_features + context_features],
    y = pairwise_rows["delta_revenue_on_existing_product"]
)

# 5) Train candidate effect generalizer
effect_generalizer.fit(
    X = pairwise_rows[candidate_features + pair_features + context_features],
    y = pairwise_rows["delta_portfolio_or_product_revenue"]
)

14.2 Candidate Scoring Phase

def score_candidate(candidate, context, current_portfolio):
    gross_adds = popularity_model.predict(candidate, context)

    new_bundle_revenue = revenue_model(candidate, gross_adds, context)

    cannibalized_revenue = 0.0
    positive_spillover = 0.0
    affected_products = []

    for incumbent in current_portfolio:
        pair_x = build_pair_features(candidate, incumbent, context)
        delta = pairwise_cannibal_model.predict(pair_x)

        affected_products.append({
            "product_id": incumbent.product_id,
            "revenue_delta": delta
        })

        if delta < 0:
            cannibalized_revenue += abs(delta)
        else:
            positive_spillover += delta

    net_incremental_revenue = (
        new_bundle_revenue
        + positive_spillover
        - cannibalized_revenue
        - estimate_launch_cost(candidate, context)
        - estimate_promo_cost(candidate, context)
    )

    lcb = lower_confidence_bound(net_incremental_revenue)

    cannibalization_ratio = (
        cannibalized_revenue / max(1.0, new_bundle_revenue)
    )

    affected_products.sort(key=lambda row: row["revenue_delta"])

    return {
        "predicted_gross_adds": gross_adds,
        "predicted_new_bundle_revenue": new_bundle_revenue,
        "cannibalized_revenue": cannibalized_revenue,
        "positive_spillover_revenue": positive_spillover,
        "net_incremental_revenue": net_incremental_revenue,
        "net_incremental_revenue_lcb": lcb,
        "cannibalization_ratio": cannibalization_ratio,
        "affected_products": affected_products[:10]
    }

14.3 GA Evaluation Loop

def fitness(candidate, context, current_portfolio):
    result = score_candidate(candidate, context, current_portfolio)

    overlap_penalty = compute_overlap_penalty(candidate, current_portfolio)
    complexity_penalty = compute_complexity_penalty(candidate)

    return (
        w1 * normalize(result["net_incremental_revenue_lcb"])
        + w2 * normalize(popularity_score(candidate, context))
        - w3 * normalize(result["cannibalization_ratio"])
        - w4 * normalize(overlap_penalty)
        - w5 * normalize(complexity_penalty)
    )

population = initialize_from_current_operator_portfolio(current_portfolio)

for generation in range(max_generations):
    scored = [(candidate, fitness(candidate, context, current_portfolio)) for candidate in population]
    selected = selection(scored)
    children = crossover_and_mutation(selected, constraints=business_rules)
    population = elitism(scored) + children

best_candidates = rank_final_population(population)

MVP Roadmap

Phase 1: Trustworthy Baseline

  • Build one-operator weekly panel
  • Create product event registry
  • Train popularity model
  • Build simple within-operator lift estimator

Phase 2: Cannibalization Intelligence

  • Build pairwise cannibalization dataset
  • Train affected-product ranking model
  • Create scenario scorer API
  • Add confidence-aware decision logic

Phase 3: Full Optimization

  • Integrate GA
  • Seed from current operator portfolio
  • Use phased launches for validation
  • Close the loop with post-launch monitoring
Final engineering rule: the optimizer must maximize risk-adjusted net incremental revenue for this single operator, not gross sales, not raw popularity, and not isolated product-level demand.
