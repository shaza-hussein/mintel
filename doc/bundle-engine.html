MinTel Bundle Engine

Telecom Bundle Engine Methodology, Approach, and Generation Process

This document explains the method used to build the telecom bundle engine: how bundle ideas are generated, why this approach is suitable for telecom offers, how candidate bundles are filtered and scored, how commercial risk is controlled, and what sequence of steps turns raw bundle history into launch-ready recommendations.

Main methodological idea: the engine does not rely on one single model. It uses a layered approach: synthetic candidate generation + business-rule cleanup + popularity prediction + pricing + portfolio impact evaluation. That layered design is the reason the process is both creative enough to generate new bundles and controlled enough to stay commercially realistic.

01

Executive Summary

The method behind the current telecom bundle engine is to treat bundle creation as a structured decision problem rather than as free-form invention. The engine first learns what realistic bundles look like from historical telecom products, then generates new candidates, filters them through business rules, estimates likely demand, and finally evaluates whether each candidate adds value to the portfolio after accounting for cannibalization.

Method in One View

  • study the current portfolio and historical bundle behavior
  • convert noisy telecom product data into structured service volumes, price, validity, and bundle-type signals
  • generate many new bundle candidates from learned historical patterns
  • remove unrealistic or commercially invalid candidates
  • estimate which bundles are likely to attract strong demand
  • price bundles consistently using the pricing logic already trusted by the business
  • compare each new bundle against the existing portfolio to estimate gain versus damage
  • rank bundles by net portfolio value instead of raw novelty

Why This Approach Makes Sense

  • Synthetic generation is needed because telecom teams want new combinations, not just copies of old products.
  • Popularity prediction is needed because many realistic bundles will still be weak offers in the market.
  • Rule constraints are needed because model outputs alone can produce odd or unbalanced bundles.
  • Pricing separation is needed because bundle design and price governance should not be mixed carelessly.
  • Portfolio simulation is needed because a popular bundle can still be commercially bad if it steals too much from existing offers.
Short answer: build the engine as a pipeline with five stages: prepare portfolio data, generate candidate bundles, enforce business realism, estimate demand, then rank by net commercial impact.
02

What This Method Is and Is Not

Before building on top of this repo, it is important to describe the current system correctly.

It Is

A structured offer-design method that combines historical learning, synthetic generation, supervised scoring, pricing logic, and portfolio-risk evaluation.

It Is Not

A pure text-generation system or a simple rule engine. The method is stronger than both because it learns from historical data but still uses explicit business controls.

Important Nuance

The best way to understand the approach is not "AI writes bundle ideas". The correct interpretation is: "the system proposes many structured bundle candidates, then filters and ranks them using telecom-specific decision logic."

Decision Style: controlled candidate generation Model Style: generative plus predictive Pricing Style: governed by pricing logic Evaluation Style: portfolio-aware Main Output: ranked bundle recommendations Main KPI: net revenue after cannibalization
03

Main Method Blocks

The generation method is easier to understand when broken into functional blocks. Each block solves a specific decision problem.

Decision Intake Layer

Input Commercial intent

The process starts from commercial choices such as offer type, allowed bundle families, validity windows, and maximum service volumes.

Control Generation boundaries

These settings act as guardrails so the engine explores only the commercial space the business is willing to consider.

Purpose Problem framing

The method is not "generate anything"; it is "generate bundles inside a controlled policy envelope".

Outcome Targeted search space

This reduces useless bundle combinations and keeps the model focused on commercially relevant candidates.

Candidate Creation Layer

Learning Historical bundle patterns

The engine learns how real telecom bundles are structured from historical products rather than inventing offers blindly.

Generation Synthetic sampling

CTGAN is used to sample new bundle combinations that resemble the telecom product space but are not limited to exact historical copies.

Cleanup Validity and volume correction

Post-generation rules remove impossible outputs and align validity and service quantities to business expectations.

Pricing Commercial repricing

Generated bundles are repriced through the pricing method so final recommendations reflect real offer economics.

Evaluation Layer

Demand Popularity estimation

A supervised model estimates which generated bundles are likely to perform strongly relative to others in the same batch.

Risk Cannibalization estimation

The engine measures how closely a new bundle competes with existing bundles and estimates revenue migration risk.

Value Net portfolio contribution

The best bundle is not the one with the highest raw demand score but the one with the best net gain after portfolio damage is considered.

Output Ranked recommendations

The final result is a ranked list of bundles, supporting KPIs, and bundle-to-bundle impact details for decision makers.

04

End-to-End Runtime Flow

This is the actual runtime path for bundle generation and ranking when the API is called.

1

Request In

Client sends offer_type, allowed bundle types, validity options, max volumes, sample count, and top_n to POST /generator/bundles.

2

Config Build

The router creates a BundleGenerationConfig instance and normalizes inputs like bundle types and offer type aliases.

3

Existing Portfolio

The generator loads historical bundles, cleans volumes and price, builds features, computes popularity, and aggregates to one row per existing bundle.

4

CTGAN Generate

A trained CTGAN synthesizer samples new bundles by segment. Fallback bootstrap is used for bundle types with too little training data.

5

Business Cleanup

Constraints enforce valid service volumes, snap validity to allowed options, cap extreme volumes, and reprice bundles through the pricing engine.

6

Popularity Score

A fitted LightGBM popularity pipeline predicts bundle popularity. Generated bundles are bucketed into Very Popular, Popular, or Unpopular by internal quantiles.

7

Portfolio Impact

Each generated bundle is compared against the live portfolio using weighted cosine similarity, utility advantage, and cannibalization rules.

8

Rank and Return

The API returns existing bundles, generated bundles, impact rows, full summary, and top bundles per bundle type ranked by net revenue.

05

How Existing Bundles Are Prepared

The engine does not compare new bundles against raw historical rows. It first constructs an aggregated representation of the current portfolio. That is the baseline the new bundles are competing against.

Source and Cleaning

  • Source path is defined in DataConfig.weekly_bundles_data_path.
  • Rows with missing configured_volume are removed.
  • Bundles containing DIY in the name are removed.
  • configured_volume is parsed into volume_mb, minutes, and sms.
  • price is normalized by stripping formatting like trailing F.

Popularity for Existing Bundles

Existing bundle popularity is not predicted by the LightGBM model. It is computed directly from observed portfolio behavior using the PopularityFunction.

R_norm = log1p(total_rev) normalized to [0,1] U_norm = log1p(unique_users) normalized to [0,1] RC_norm = log1p(rev_contribution_pct) normalized to [0,1] popularity_score = 0.50 * R_norm + 0.25 * U_norm + 0.25 * RC_norm
Aggregated Field How It Is Built Why It Matters
bundle_name first value per bundle_id Human-readable identity for impact reporting.
price first cleaned price per bundle Used in utility and revenue calculations.
volume_mb, minutes, sms max value per bundle Defines the product feature vector used in similarity scoring.
avg_weekly_revenue mean of total_rev Baseline revenue at risk from cannibalization.
avg_weekly_subs mean of total_subscriptions Used to estimate migration and new subscriber impact.
popularity_score max computed popularity per bundle Represents observed attractiveness of the current offer.

How Synthetic Bundles Are Generated

New bundles are created by a trained BundleCTGANSynthesizer. The model learns the joint structure of historical bundle attributes and then samples new bundle candidates per bundle type.

CTGAN Training Representation

The synthesizer is trained on these bundle columns:

  • bundle_type
  • usage_type
  • service_class_category
  • price
  • volume_mb
  • volume_min
  • volume_sms
  • validity_hours

Sparse numeric columns are encoded with additional presence flags, so the model can learn the difference between "zero because absent" and "zero because small".

Segment-Aware Generation

  • The synthesizer groups training data by bundle_type.
  • If a segment has at least min_rows_for_ctgan = 100, a CTGAN model is trained for that segment.
  • If a segment has too few rows, the engine falls back to bootstrap resampling with small numeric noise.
  • Generation happens per segment, then results are concatenated.

Business Constraints Applied After Sampling

  • price is clipped to at least 1 before repricing.
  • Negative or invalid service volumes are clipped to 0.
  • validity_hours is snapped to the nearest allowed validity option.
  • Data bundles with unrealistically tiny MB volumes are lifted toward a segment median.
  • Voice bundles with unrealistically tiny minute values are lifted toward a segment median.
  • Rows with zero total service content are removed.
  • Final bundle-type-specific max volume constraints are enforced.

Final Cleanup and Repricing

  • Data-only bundles are forced to have zero minutes and zero SMS.
  • Voice bundles are forced to have zero data MB.
  • SMS bundles are forced to have zero MB and zero minutes.
  • Extreme numeric volumes are capped against the 0.999 quantile of real training data.
  • Prices are recalculated using BundlePricingService and the existing dynamic pricing engine.
  • Final prices are clipped to a minimum of 5.
Design decision worth keeping: price is not learned from the CTGAN output as the final commercial truth. The engine reuses the pricing engine to keep bundle generation aligned with the operator's pricing policy.

How Popularity Is Predicted for Generated Bundles

Generated bundles are passed through a trained popularity pipeline. This step estimates how attractive the generated offer may be before the engine considers its revenue and cannibalization effects.

Feature Engineering Logic

  • Inference rows are given the current ISO year and week number.
  • If missing, bundle_name is set to an empty string.
  • Configured service volumes are derived from generated numeric values.
  • Season is inferred from the week number.
  • Bundle name parsing extracts signals such as data amounts, minutes, SMS, unlimited flags, social keywords, roaming, and speed tokens.
  • Derived features include logs, service presence flags, combo indicators, validity buckets, and cyclic week features.

Modeling Choice

The pipeline uses LightGBM regression, wrapped in PopularityRegressor. That is a good fit for this problem because bundle attractiveness depends on nonlinear interactions between price, validity, service mix, and category.

Categories are handled with controlled rare-value grouping inside LGBMDataPreparer, which helps keep inference stable when new categorical combinations appear.

Popularity Categories for Generated Bundles

predicted_popularity = LightGBM(bundle_features) p40 = 40th percentile of predicted_popularity within generated sample p80 = 80th percentile of predicted_popularity within generated sample if score >= p80 -> "Very Popular" elif score >= p40 -> "Popular" else -> "Unpopular"

Important Interpretation Detail

These popularity categories are relative to the generated candidate set, not absolute market-wide thresholds. That means "Very Popular" here really means "top-scoring among the sampled synthetic bundles for this run".

The runtime generator currently keeps only bundles in the configured popularity buckets. By default this is ("Very Popular",), so the engine aggressively filters for the top predicted candidates before simulation.

How Cannibalization and Portfolio Value Are Calculated

The engine does not stop at popularity. It simulates the effect of every generated bundle on the current portfolio and ranks bundles by estimated weekly net revenue.

Similarity Features

Existing and generated bundles are converted into comparable feature vectors using:

  • volume_mb
  • minutes
  • sms
  • price
  • validity_days

The current weights are 1.0 for data, minutes, SMS, and price, and 0.5 for validity.

Similarity Function

Feature values are normalized against maxima from the existing portfolio, then compared with a weighted cosine similarity.

similarity = weighted_cosine(normalized_new_bundle, normalized_existing_bundle) if bundle types differ: similarity = similarity * 0.4

The code multiplies similarity by 0.4 across different bundle types. In the API metadata this is exposed as cross_type_penalty = 0.6, which effectively means a 60% penalty and 40% retained similarity.

Utility Function

utility(popularity, price) = (popularity / price) ^ price_elasticity price_elasticity default = 1.50

This favors bundles that deliver more predicted popularity per unit price, adjusted by elasticity.

Cannibalization Rate

if similarity < similarity_threshold: cannibalization_rate = 0 else: advantage = max(0, (new_utility - existing_utility) / existing_utility) rate = cannib_sensitivity * similarity * min(advantage * 0.5, cannib_cap) rate = min(rate, cannib_cap) defaults: similarity_threshold = 0.05 cannib_sensitivity = 0.5 cannib_cap = 0.25
KPI How It Is Derived Meaning
incremental_revenue_weekly new_subs_weekly * new_price Gross added weekly revenue from the new bundle.
total_cannib_revenue_weekly sum of existing bundle revenue losses Revenue stolen from the current portfolio.
net_revenue_weekly incremental_revenue_weekly + total_cannib_revenue_weekly Main ranking KPI used to sort generated bundles.
cannib_pct_of_portfolio absolute cannibalized revenue / total existing revenue Portfolio damage indicator.
risk_tier based on cannibalization rate thresholds high above 10%, medium above 5%, low above 0%, else none.
Why this step is valuable: a bundle can be attractive on its own but still be a bad launch decision if it mostly steals revenue from current products. Ranking by net revenue after cannibalization is the right business framing.

How the Engine Learns Before Generation

The runtime generation process depends on prior learning. The system must first learn what realistic bundles look like and what bundle patterns are associated with strong popularity.

Learning Demand Patterns

One part of the method learns which bundle shapes tend to be commercially attractive.

  • historical weekly bundles are cleaned and standardized
  • a popularity target is built from revenue, user adoption, and revenue contribution
  • bundle attributes are transformed into a richer feature space, including service mix, validity, price, and bundle-name signals
  • a supervised model learns how these features relate to popularity
  • the fitted model is reused later to score generated bundles

Learning Bundle Structure

Another part of the method learns the shape of realistic telecom bundles.

  • historical offers are grouped by bundle family so the model learns data bundles differently from voice or SMS bundles
  • CTGAN learns mixed tabular patterns across service type, price, validity, and service volumes
  • small bundle families use bootstrap fallback to avoid unstable training
  • the trained generator is then used to sample fresh bundle candidates during runtime

What the Generation Process Produces

A useful bundle engine must return more than just a list of generated bundles. Decision makers need both bundle candidates and the reasoning signals that explain why those candidates are worth considering.

Inputs to the Process

{
  "offer_type": "atl",
  "allowed_bundle_types": ["BUNDLE_DATA", "BUNDLE_VOICE", "BUNDLE_SMS"],
  "validity_options": [24.0, 72.0, 168.0, 720.0],
  "max_volume_mb": 25000,
  "max_volume_min": 300,
  "max_volume_sms": 150,
  "samples_per_type": 500,
  "top_n": 2
}

Outputs That Matter

  • a clean view of the existing portfolio used as the comparison baseline
  • the generated bundle set that survived filtering and business constraints
  • bundle-level commercial summaries such as predicted popularity, incremental revenue, cannibalized revenue, and net revenue
  • top-ranked bundles per bundle type so the business can compare strong data, voice, and SMS options separately
  • detailed impact rows showing which existing bundles are most exposed to each new recommendation
A strong output design is part of the method itself. Bundle generation is only useful when the result is interpretable enough for product, pricing, and marketing teams to review and act on it.

How to Build the Telecom Bundle Engine Now

Based on the current source code, this is the correct practical approach to get the engine into a usable state.

Phase A: Stabilize Inputs and Artifacts

  1. Make the weekly bundle dataset available at the configured path or update DataConfig to the correct location.
  2. Validate that the CSV contains the columns expected by RawBundlePreprocessor and popularity training.
  3. Confirm that the two fitted artifacts can be loaded successfully in the runtime environment.
  4. Keep the pricing configuration aligned with the telecom operator's commercial rules.

Phase B: Keep the Current Core Architecture

  1. Use CTGAN for candidate generation.
  2. Use LightGBM for popularity prediction.
  3. Keep dynamic pricing as the price authority.
  4. Keep portfolio simulation as the final ranking layer.
  5. Expose the result through the existing FastAPI endpoint.

Phase C: Recommended Engineering Refinements

  • Refactor the router so it calls public generator methods rather than private methods.
  • Unify data-path configuration in one place and make it environment-driven.
  • Add explicit schema validation for the training CSV before preprocessing starts.
  • Persist run metadata for reproducibility, including config, artifact version, and request payload.
  • Add tests for generation filters, popularity bucketing, and cannibalization calculations.

Phase D: Recommended Product Refinements

  • Move from relative popularity buckets to calibrated probability or expected-demand outputs.
  • Add margin or cost-to-serve logic, not just revenue logic.
  • Add customer segment or audience targeting after bundle selection.
  • Add human approval gates before launch.
  • Add monitoring for model drift, generated bundle novelty, and pricing anomalies.

Suggested Build Sequence

1. Fix dataset path and validate raw weekly bundle data.
2. Train or reload the popularity pipeline artifact.
3. Train or reload the CTGAN synthesizer artifact.
4. Start FastAPI with the generator router enabled.
5. Call POST /generator/bundles with generation constraints.
6. Use top_per_type and summary as the commercial recommendation layer.
7. Review impact_rows to understand which existing bundles are most at risk.
8. Add dashboard, approval, and monitoring around this core engine.
Best architecture decision already present in the code: generation, popularity, pricing, and cannibalization are separated into clear modules. That makes the engine much easier to improve incrementally without rewriting the whole system.

Current Risks, Limits, and Implementation Notes

The engine is solid as a technical prototype and a strong base for a production system, but several limitations are visible in the current code.

Path Reliability

The configured dataset path is a hard dependency and is currently unresolved in this workspace. Until that is fixed, training and existing-portfolio loading are fragile.

Relative Popularity Buckets

The "Very Popular" filter is based on quantiles of the generated sample, so it is stable within a run but not directly comparable across runs.

Private API Usage

The router is calling private methods of the generator class. It works now, but it couples the API to class internals more than it should.

Revenue but Not Margin

Ranking is based on revenue and cannibalization, not on gross margin, network cost, or subsidy economics.

No Audience Layer Yet

The engine selects bundles, but it does not yet decide which customers or segments should receive each one in the active runtime path.

No Workflow Governance

There are no approval, rejection, audit, or launch-control workflows around the engine yet. Those are still external concerns.

Practical Implementation Notes

Observation Why It Matters
The generator method is named __exiting_products. This looks like a typo of "existing", but it is consistently used, so behavior is correct. It is only a readability issue.
API request default validity options differ from BundleGenerationConfig defaults. The API route overrides the config defaults, so runtime behavior follows the request model values, not always the config file defaults.
The API reports cross_type_penalty = 0.6 while the model multiplies similarity by 0.4. This is not necessarily wrong, but it should be documented clearly as "60% penalty, 40% retained similarity".
Generated popularity filtering happens before portfolio simulation. This reduces computational load and narrows search space, but it can remove bundles that might have lower popularity yet better portfolio economics.

Final Technical Position

The current codebase already contains a real bundle engine, not just disconnected experiments. Its strongest form is: historical portfolio preprocessing + CTGAN-based bundle creation + dynamic repricing + LightGBM popularity scoring + cannibalization-aware portfolio ranking.

If you want to build the telecom bundles engine now, the right next move is not to replace this design with a generic generative AI layer. The right move is to operationalize the existing architecture, fix the data-path dependency, add tests and governance, and then extend it with targeting, margin logic, and production monitoring.

In other words: the code already solves the hard core of bundle generation. The next stage is productization and control, not a fresh redesign.
